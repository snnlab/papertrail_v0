description: Host a classroom roster server for many students to submit to — instructor-only, separate from the per-project board
argument-hint: [--init | --add-student <name-or-id> | --roster <file> | --deploy | --roster-view | --rotate-token <studentId>]
allowed-tools: Read, Write, Edit, Glob, Grep, AskUserQuestion, Bash(python3:*), Bash(git:*), Bash(ls:*), Bash(date:*), Bash(cp:*), Bash(mkdir:*), Bash(npx:*), Bash(vercel:*), Bash(node:*), Bash(curl:*)
---

Run and manage the instructor's classroom roster server: one Vercel project, shared by every student in a course, that `/papertrail:submit` sends each student's project state to. This is a **separate, new surface** from `/papertrail:board`'s `--publish-web` (one project per student, one shared password) — a different trust model (per-student bearer tokens, an instructor-only login) needs its own project. Nothing here changes anything about a student's local board, sign-off gate, or `--publish-web` link.

**Scope note, unlike every other `/papertrail:*` command:** this command runs from the **instructor's own working directory** — a directory for course administration, not a student's initialized project. It does not require and does not check for `plans/master-plan.md`. Materialize everything it needs under `plans-admin/` in that directory (create it if absent), never under `plans/` — `plans-admin/` is course-administration state, not project/plan content, and must be git-ignored.

**Hard invariant, carried over from the single-project board (`AGENTS.md`'s "Comment-only instructor role"):** this command never gains a `--sign`, `--approve`, or any other action that overrides or bypasses a student's own sign-off. It registers students, mints and rotates their tokens, deploys the server, and opens the dashboard — nothing that touches plan authorship or approval. If a future change to this file would add such a verb, that is a violation of the project's design, not a feature.

1. **Resolve the mode from `$ARGUMENTS`.** With no argument, read `plans-admin/.classroom-web/` config if present (see First-run setup) and report status: whether a server is configured, its URL, and how many students are registered (`GET /api/roster`, authenticated per step 2's login helper). If nothing is configured yet, suggest `--init`. Otherwise dispatch to the matching step below.

2. **Shared helper: authenticate as the instructor.** Several modes below need an authenticated session against the deployed server. `POST <url>/api/login` with `{"password": "<BOARD_PASSWORD>"}` (read from `plans-admin/.classroom-web/.env.local` or wherever step 3 recorded it) via `curl -s -c <cookiejar> -X POST <url>/api/login -H 'Content-Type: application/json' -d '{"password":"<password>"}'`, then reuse `-b <cookiejar>` on every subsequent authenticated call in this session. Never print the password to the transcript; read it from the local file, not by asking the student/instructor to retype it each time.

3. **`--init` — first-run setup.** Conversational, not a single call, and mirrors `--publish-web`'s own first-run pattern (`skills/managing-papertrail/references/web-publishing.md`) closely enough that anyone who has set up the single-project board once will recognize every step. One-time, about 20 minutes; every later `--deploy` is one click. Complete these in order:
   - **Preflight Node.** Check `node --version` and `npx --version`; if either is missing, point at nodejs.org or `brew install node` and stop.
   - **Check the Vercel CLI.** `npx vercel --version` (needs 50.20+; `npx` fetches it on demand).
   - **Login.** Ask the instructor to run `vercel login` in their **own terminal**, not this session (no TTY here for it), then verify with `npx vercel whoami`. Never attempt `vercel login` yourself.
   - **Materialize the deploy directory.** `mkdir -p plans-admin` if absent, then copy the template: `cp -r "${CLAUDE_PLUGIN_ROOT}/skills/managing-papertrail/assets/classroom-template" plans-admin/.classroom-web` (skip `node_modules`, `.vercel`, and `*.test.ts` if present). If `plans-admin/.classroom-web/` already exists, this is a reconnect/redeploy, not a fresh setup — skip to **Set the secrets** or `--deploy`.
   - **Write the dashboard shell.** The copied template has no `index.html` of its own (same as `web-template/` — it's generated, not checked in). Write one with `board.py`'s new `render_roster_html()` helper, which takes the same prebuilt single-file board bundle every student's board already uses and marks its root div so the bundle boots into the roster dashboard instead of a single-project board, with no embedded payload (the dashboard fetches `/api/roster` live instead): `python3 -c "import sys; sys.path.insert(0, '${CLAUDE_PLUGIN_ROOT}/skills/managing-papertrail/scripts'); import board; open('plans-admin/.classroom-web/index.html', 'w', encoding='utf-8').write(board.render_roster_html())"`. Re-run this any time the plugin's board bundle is updated, before the next `--deploy`.
   - **Create or link the project.** `cd plans-admin/.classroom-web && npx vercel link` to create a new Vercel project (name it something like `<course>-roster`, distinct from any per-student board projects).
   - **Create and connect a PRIVATE Blob store.** `npx vercel blob create-store <name> --access private` (the `--access private` flag is required — a public store defeats both the instructor password gate and the whole point of per-student bearer tokens). Connecting it to the project is an interactive dashboard step exactly as in `--publish-web`: **Storage > Connect Store**, check **Production**, connect. Confirm it shows **Access: Private**. Its region is fixed at creation — for a classroom roster this is a bigger surface than one student's board (every registered student's decision log and git history, not one project's), so if data residency matters, choose deliberately; see `docs/hosting-the-roster.md`'s privacy section before proceeding.
   - **Set the secrets.** Same stdin pattern as `--publish-web` (never a CLI argument — it would leak into shell history): `printf '<value>' | npx vercel env add <NAME> production`, then again with `development`. Set:
     - `BOARD_PASSWORD` — the instructor's own login passphrase. Reuse the existing generator: `python3 -c "import sys; sys.path.insert(0,'${CLAUDE_PLUGIN_ROOT}/skills/managing-papertrail/scripts'); import board; print(board.generate_passphrase())"`. Fine for one human-typed password.
     - `BOARD_SESSION_SECRET` — a fresh random value, e.g. `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`. Never shown or reused elsewhere.
     - `ROSTER_TOKEN_PEPPER` — a second, independent fresh random value, same command. This is **not** the same secret as `BOARD_SESSION_SECRET` — it peppers student bearer-token hashes, a completely different purpose from the instructor's cookie signing key. Generate it separately.
     - `COURSE_ID` (optional) — a short id shown in the roster payload's `course.id`, e.g. `soc-501-fa26`.
     `BLOB_READ_WRITE_TOKEN` is set automatically when the Blob store is connected — do not set it manually.
   - **Enable firewall rate limiting** on the `/api/login` route in the project's Vercel Firewall settings, exactly as `--publish-web` requires. Do not deploy until this is enabled.
   - **First deploy.** `npx vercel deploy --prod --yes` from `plans-admin/.classroom-web/`.
   - **Record the URL locally.** Write `plans-admin/.classroom-web-config.json` (git-ignored — add `plans-admin/` to a `.gitignore` if one is not already covering it) with `{"url": "<deploy url>"}`, so later invocations of this command don't have to ask again.
   - Report the deployed URL and remind the instructor: nothing here sends student invitations or tokens — that is entirely `--add-student`/`--roster` below, and even then, this tool does not send email (see step 4).

4. **`--add-student <name-or-id>` / `--roster <file>`.** Registers one student (a name or id given directly) or bulk-registers from a file (`--roster <path>`, one `id,displayName` pair per line, or a simple CSV the instructor already has — accept either a comma or the whole line as the display name if no comma is present and ask for clarification if the format is ambiguous). For each student:
   - `POST <url>/api/roster` (authenticated per step 2) with `{"studentId": "<id>", "displayName": "<name>"}`. If the student already exists, this **mints a fresh token and invalidates the old one** (see `--rotate-token`) — the server has one registration endpoint that also serves as rotation, so warn the instructor before re-running `--add-student`/`--roster` for someone already registered, in case they didn't intend a rotation.
   - Collect every returned `{studentId, displayName, token}` into one table.
   - **Print the table** in the transcript, and **also write it** to a local, git-ignored file — `plans-admin/roster-tokens-<YYYY-MM-DD>.csv` (real date via `date +%F`), columns `studentId,displayName,token,url`. This lives under `plans-admin/`, deliberately **outside** any `plans/` directory, so it is never mistaken for project or plan content, and confirm `plans-admin/` is git-ignored before writing anything sensitive into it.
   - State explicitly, matching `docs/hosting-the-board.md`'s existing "you send it yourself" pattern: **this tool does not send email or any other message to students.** Copy each student's token out of the CSV into whatever the instructor already uses — the LMS, a mail merge, individual messages — themselves. A token is a personal credential for one student; treat distributing it with the same care as a password, never a shared class announcement.

5. **`--deploy`.** Redeploy after any roster or secret change: `npx vercel deploy --prod --yes` from `plans-admin/.classroom-web/`. Idempotent — safe to run any time nothing needs deploying too.

6. **`--roster-view`.** Print the dashboard URL (`<url>/`, from the local config) and remind the instructor it asks for the login password set in `--init` — the same instructor login used throughout this command, not a per-student token. Open it if the environment supports opening a URL; otherwise just print it. Mention two things about the view itself: a **"new" badge** marks any row submitted since the instructor's own last visit to this dashboard (computed server-side from a single last-viewed pointer — there being only one instructor login, this needs no per-person state); and clicking into a student's board there works exactly like a `--publish-web` collaborator link — select text, leave a comment — because it reuses that same hosted-comment machinery, just scoped per submission on this shared server instead of one deployment per student. There is still no student-facing notification for a new comment; the student only learns about it the next time they run `/papertrail:submit`, which checks and prints anything new.

7. **`--rotate-token <studentId>`.** Mints a fresh token for one student and invalidates the old one immediately (the server deletes the old token's reverse-index entry as part of this — see `lib/roster.ts`'s `upsertStudent`). Look up the student's current `displayName` first via `GET <url>/api/roster` (authenticated), then `POST <url>/api/roster` again with the same `studentId` and that `displayName` — this is the same registration endpoint as `--add-student`, since re-registering an existing student **is** how rotation happens; there is no separate rotate endpoint. Print the new token and state plainly that the previous token no longer works — anything relying on it (a student's saved `submit.py` config) will get `401 invalid_token` until the student is given the new one and re-runs `/papertrail:submit` with it.

8. **Close out.** After any mutating mode (`--init`, `--add-student`/`--roster`, `--rotate-token`), suggest `--deploy` if a redeploy is actually needed (registering or rotating a student does **not** require a redeploy — those are pure Blob writes the running server already serves; only a code or secret change does). After any mode, remind the instructor that `--roster-view` opens the dashboard, and that the roster surfaces a **trust-tier legend** (mechanically re-verified vs. timing/similarity signals vs. self-reported) — read it, and read `docs/hosting-the-roster.md`'s data/privacy section before relying on the green checks alone.
